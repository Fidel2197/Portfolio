My approach

How I build.

How I plan a project, organize the code, and check that it works.

Planning

I start with the main task and sketch the screens it needs. For DataDock, that is uploading a CSV, reviewing its issues, and downloading a cleaned file. I also decide what should be saved and whether it belongs to a browser, guest session, or account.

Code structure

I split larger pages into smaller components and keep request handling separate from the interface. In SnapChef, upload controls, recipes, accounts, and history have separate components. SignalDesk uses separate dashboard views and a shared progress store.

Data and accounts

I check who can read or change saved data. DataDock checks report ownership in its API. SnapChef uses Supabase accounts and database policies. Projects that use localStorage keep their data in the current browser.

Testing

I test ordinary use and failure cases: invalid files, rejected requests, sign-out, deleted records, and page refreshes. Automated checks cover report ownership in DataDock, recipe history in SnapChef, and saved incident progress in SignalDesk.

Fixes from feedback

DataDock’s sidebar once clipped its account controls. I moved sign-in higher, added a collapse button, and fixed the scrolling. In SignalDesk, I added browser storage after finding that incident changes disappeared on refresh.

Publishing

I keep the source on GitHub and deploy the web apps on Vercel. The main projects run automated checks on pushes and pull requests. Their repositories include setup steps, environment settings, and notes about storage and current limitations.
