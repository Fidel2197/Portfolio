My Approach

How I turn an idea into something people can actually use.

I try to build projects like products, not just assignments. That means I think about the person opening the page, the main action they need to take, the information they need first, and the details that make the project easier to review.

Working style Plan the user flow, build the smallest useful version, test the behavior, then polish the explanation.
User flow Behavior Review notes
01

Start with the user's question

Before I build screens, I decide what the user is trying to answer. For SnapChef, that question is "what can I make from this food?" For SignalDesk, it is "what broke, where is it, and what should the team do next?"

02

Create a simple first path

I make sure the first screen has a clear purpose. I avoid putting every feature on the homepage when a separate page, tab, or focused workspace would make the project easier to understand.

03

Build the real interaction

I add behavior that proves the interface is usable: uploads, saved records, filters, status updates, navigation, game controls, form feedback, and state changes that a reviewer can test.

04

Polish for review

I check spacing, mobile layout, screenshots, links, README notes, live deployment behavior, and project descriptions so the work is easier for recruiters and teammates to evaluate.

Decision Board

Questions I ask while building.

These questions keep the project from becoming a pile of features. They help me decide what the user sees first, what should become a separate page, and what a reviewer should be able to test.

What is the first useful action? Upload food, review an incident, start a study plan, open a game, or submit a form.
What information should not be on the homepage? Detailed reports, profile settings, saved history, advanced filters, and long instructions belong in focused views.
What proves the project works? Clickable navigation, changed state, saved records, form feedback, visible results, and a live deployment.

How this shows up in my projects

SignalDesk uses separate app views because a response workspace should not overload the user on the first screen. SnapChef uses saved scan history and result sections because food analysis needs a clear path from upload to recipe. StudyOps organizes study work into files, notes, tasks, flashcards, quizzes, and planning tools.

How I explain the work

I write project cards and READMEs with the same structure: what problem the project solves, what I built, what technologies I used, and what someone should try first when opening the live site.

SnapChef

SignalDesk
